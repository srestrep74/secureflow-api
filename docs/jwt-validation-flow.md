# JWT Validation

Phase 5.1B implements structural validation only. Enabling JWT requires `secureflow.jwt.issuer` and `secureflow.jwt.audience` in addition to the external RSA key properties. These trusted values are operator configuration, never selected from the token. The configured public key and `kid` are the only trusted key; RS256 is the only accepted algorithm.

The protected header is `alg: RS256`, `kid` equal to the configured key ID and `typ: JWT`. The signed payload requires `iss`, `aud` (a nonempty string or string array containing the configured audience), `sub`, `jti`, `sid`, `iat`, `nbf`, `exp`, `token_use: access`, `security_version`, `catalog_version`, `roles` and `permissions`. Identifiers are canonical lowercase UUID strings. Versions are JSON integers: security version is nonnegative; the supported catalog version is 1. Roles are a nonempty array of unique `ROLE_USER`, `ROLE_AUDITOR` or `ROLE_ADMIN` strings. Permissions are a unique string array exactly matching the union of the approved grants for those roles. No email or secret is included. The fixed catalog is implemented in the JWT infrastructure and must be coordinated with the future durable catalog migration.

The issuer receives an existing user UUID, session-family UUID, versions and roles; it cannot create a session. It generates a fresh `jti`, takes UTC time from a clock and signs with `NimbusJwtEncoder`. The issued-at and not-before values are the same second, and expiration is exactly five minutes later. Tokens have no public issuing endpoint.

`NimbusJwtDecoder` verifies the signature and algorithm; its composed validators enforce the trusted key ID, issuer, audience, mandatory expiration and not-before, and the project-specific claims. Timestamps must be numeric dates, expiration must be after issuance, not-before cannot be after expiration, issued-at cannot exceed the current time by more than 30 seconds, and declared lifetime cannot exceed five minutes. Spring's timestamp validator applies the approved 30-second skew to expiration and not-before. The skew permits acceptance shortly outside the nominal window but does not extend the declared lifetime. Invalid types, absent claims, unsupported versions, unknown roles or permissions and mismatched snapshots fail closed.

A verified token is not an authorization decision. HTTP Resource Server integration, current account status, session ownership/revocation and matching the user and catalog versions against PostgreSQL are not implemented. ADR-0004 requires a `SecurityStatePort` read before accepting the snapshot; failure or stale state must not fall back to signed claims. No persistence lookup occurs in Phase 5.1B.

The persisted family UUID is compatible with the `sid` claim. A valid signature alone cannot establish that the session is active. Phase 5.4 must query the primary database for user and family state and the durable catalog version; initialize the singleton catalog at version 1 in that phase and require agreement with the binary. No PostgreSQL catalog is initialized here. Phase 5.3A connected issuance to the transactional session login flow; durable catalog checks remain future work.

## Phase 5.3A issuance

Login signs an RS256 access token inside the session-creation transaction using the locked user's current roles and security version and the persisted family ID as `sid`. Permissions come from the server catalog. The existing issuer generates the unique `jti`, issuer, audience, purpose and five-minute lifetime. Catalog version 1 is currently a code constant, not an authoritative persisted version; catalog freshness and per-request PostgreSQL validation remain Phase 5.4 responsibilities. Signing or commit failure prevents a successful application result and rolls back session creation.

## Phase 5.4A: authoritative security state

`SecurityStatePort` retrieves an immutable, minimal account, family and catalog projection using the verified subject and `sid`. `SecurityStateValidator` accepts framework-independent trusted claims and rejects missing or inactive accounts, absent or foreign families, revoked families, families outside their creation-to-expiry interval, and mismatched user or catalog versions. It does not load roles, credentials or refresh-token history. Invalid state returns false; a query failure or missing/incompatible catalog raises `SecurityStateUnavailableException` with a sanitized message. A future HTTP adapter must distinguish invalid state (401) from reliably identified unavailability (503) before trusting JWT authorities. HTTP Bearer authentication is not implemented in 5.4A.

The PostgreSQL adapter uses one parameterized statement with primary-key lookups and a singleton catalog lookup. PostgreSQL READ COMMITTED supplies one statement snapshot: all projected values reflect the same snapshot, without row locks. A change committed after the query starts may not affect that request, and an already authorized operation may finish after revocation. Stronger guarantees for sensitive writes require transaction-specific locking and rechecks. This read costs one database round trip and a connection; no benchmark or representative query plan has been measured. No cache or aggregate hydration is used.

## Phase 5.4B HTTP bearer integration

NimbusJwtDecoder enforces RS256, the trusted key ID, issuer, audience, lifetime, purpose and required claims. The converter maps the verified subject, session and versions to TrustedSecurityClaims and performs one PostgreSQL state projection before accepting roles and permissions. It creates JwtAuthenticationToken only after successful validation; no successful state is cached. Invalid claims or stale state result in 401; missing or incompatible catalog metadata and database failures result in 503.
