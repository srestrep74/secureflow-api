# Phase 0 consolidated design

**Status: Phase 0 approved on 2026-11-15.** ADR-0001 through ADR-0005 are Accepted. Phase 1 bootstrap is authorized; later phases remain gated. `initial-prompt.md` remains the requirements baseline.

## Scope and boundaries

One Spring MVC deployment, PostgreSQL, Identity & Access and Task Management capability modules. Identity owns users, credentials, fixed role grants and session families; Task owns tasks. Authentication remains inside Identity. No microservices, browser frontend, distributed cache, generic authorization engine or external IAM. Domain depends on neither Spring nor application; application depends on domain; adapters depend inward. Public application contracts, not persistence internals, cross module boundaries. Shared IDs are minimal neutral values where needed, not a shared business model.

User is an aggregate root with identity, password hash, status and assigned roles. It enforces valid status/role changes; registration always creates USER. Username is trimmed ASCII `[a-zA-Z0-9._-]`, 3–32 characters, compared case-insensitively using a lowercase canonical key. Email is trimmed, ASCII, 3–254 characters, case-insensitive for this product, with a canonical lowercase key and practical format validation; this intentionally trades full internationalized email support for unambiguous MVP semantics. Preserve display values separately if desired. PostgreSQL unique constraints on canonical keys settle races; collisions become 409, not a claim that the aggregate enforces global uniqueness. Passwords: 12–128 Unicode characters, no silent truncation, reject oversized UTF-8 input safely; use Argon2id through a maintained encoder with measured parameters. Never normalize passwords or log them.

Task root has immutable owner ID, nonblank trimmed title of 1–200 characters, optional description up to 4000 characters, status, timestamps and version. TODO → IN_PROGRESS → DONE; IN_PROGRESS → TODO and DONE → IN_PROGRESS are allowed; same-state transitions are idempotent. Completed tasks remain editable. Delete is hard delete, no restoration; no owner transfer. Commands create, edit, transition and delete are checked against invariants and optimistic version. A client supplies the version on mutations; stale writes return 409, without disclosing resource existence before authorization. Repository ports load/save aggregates and provide bounded projections; DB unique/FK constraints and conditional version updates protect integrity. Identity and Task transactions remain local, with an owner FK where feasible without exposing JPA models.

Role is a fixed code-defined catalog, not an aggregate: USER, AUDITOR, ADMIN and their grants below. Role assignments are persisted; catalog changes are deployed deliberately, increment a global catalog version included in validation, and require a migration and tests. Do not model arbitrary permissions as mutable records or introduce a policy engine. `UserId`, `TaskId` and `TaskTitle` merit value semantics; add other wrappers only for demonstrable invariants. Refresh family is a technical consistency root, not a business aggregate required to depend on the User aggregate. Its records hold token digests and lifecycle state. An application policy decides access from an immutable actor, permission and owner ID; domain validates task state and does not depend on application actor. No domain service unless an actual invariant warrants one.

## Authorization

Roles are `USER`, `AUDITOR`, `ADMIN`; framework role authorities are `ROLE_USER`, etc. Permission authorities are exact lowercase codes. Multiple roles union grants; no implicit inheritance between roles. USER: `task:create`, `task:read:own`, `task:update:own`, `task:delete:own`. AUDITOR: `task:read:any`. ADMIN: `task:create`, `task:read:any`, `task:update:any`, `task:delete:any`, `user:read:any`, `user:role:assign`, `user:status:update`. Any scope subsumes own for the same action only. `/me` requires authentication; `/tasks/mine` requires read-own or read-any and always filters by actor. `/tasks` requires read-any. Administrative user list requires user-read-any.

Deny unknown routes by default; an explicit method/path allowlist covers registration, login, refresh and logout, the latter two authenticated by refresh credential in the body. Framework checks are coarse; use cases enforce resource authorization once through a central application policy. Missing/invalid credentials yield 401; authenticated caller lacking any permission for an action gets 403; caller with own scope targeting a nonexistent or foreign task gets 404 for read, update and delete; any-scope callers get 404 for nonexistent task. Own lists are owner-filtered at the database; an empty list is 200, never an existence oracle. Pagination and sorting are bounded and allowlisted. 403 and 404 rules must be ordered consistently before returning version conflicts.

## Security state and authentication

Recommend RS256 with at least 2048-bit RSA keys, fixed algorithm, trusted key IDs and overlap during planned rotation; private keys come from deployment secrets. Access JWT TTL 5 minutes, 30 seconds maximum clock skew, validated `iss`, `aud`, `sub`, `exp`, `iat`, `nbf` when present, purpose `access`, family ID, user security version and catalog version. JWT also contains a strictly validated signed snapshot of effective roles and permissions, issued by the server. Reject absent required claims, invalid algorithm, unknown keys and malformed claims. Resource Server verifies the signature and mandatory claims before interpreting the snapshot or using `sub` and family ID as query parameters. An unknown role, permission or catalog version fails closed. After the authoritative version check succeeds, the security adapter converts the signed snapshot into authorities; it does not load roles on each request.

The application-facing `SecurityStatePort` accepts validated subject ID and family ID and returns only a security-state projection or absent; its PostgreSQL adapter owns the SQL. One parameterized, read-only statement reads the primary database at READ COMMITTED, without aggregate hydration or a second role query. Conceptually `SELECT u.status, u.security_version, f.status, f.expires_at, c.version FROM users u JOIN refresh_families f ON f.user_id = u.id JOIN security_catalog c ON c.id = 1 WHERE u.id = :subject AND f.id = :family`; aliases and schema are illustrative. Use unique/primary-key B-tree indexes on `users.id`, `refresh_families.id`, and `security_catalog.id`, with an FK from family to user; verify the actual plan with production-representative cardinalities and `EXPLAIN (ANALYZE, BUFFERS)` in an isolated test environment. No extra composite index is presumed useful without evidence. A single statement sees one PostgreSQL snapshot: require active user, matching user and catalog versions, active unexpired family owned by subject, and a locally supported catalog version. Missing/mismatched/expired state yields 401; dependency failure yields 503, never a fallback to cached or JWT-only authority. Capture one trusted current time for expiry comparison. No cache or read replica is used in the MVP.

On an effective user role assignment or removal, account status change, password/credential reset, or administrator-forced global logout, increment the user's monotonic security version in the same transaction as that change; a no-op role/status request does not increment it. Concurrent updates must serialize or use an atomic increment, and overflow must fail rather than wrap. Session-specific logout/replay revokes the family in its own transaction and does not require a user version increment. Registration initializes the version. Any fixed role-to-permission catalog change atomically increments the durable singleton catalog version in its migration. Each application binary declares the exact catalog version it understands: reject authentication and issuance if DB and binary versions differ. Deploy catalog changes with coordinated rollout or maintenance so old and new binaries cannot mint or accept authorities under a mismatched catalog. Catalog changes invalidate all previous JWTs.

Login and refresh issue a new signed snapshot from current persisted roles and the matching code catalog, together with the exact user and catalog versions used to derive it. In the issuing transaction, lock/recheck the user and read role assignments and catalog version consistently; role changes acquire the same user lock and catalog deployment is coordinated. Do not combine a newly incremented version with stale role data. Refresh can issue current authorities after a role change only if the user and family remain active; account disablement rejects refresh. Requests with previously issued version mismatches are rejected after the change commits. This preserves authoritative PostgreSQL state without a role lookup on every access request. An individual access JWT is not separately denylisted; revoke its family instead.

This trades an indexed DB read per request and DB availability for freshness, versus stateless JWTs that retain privilege until expiration. Database failure fails closed with 503, not 401 and never a fallback to JWT claims; bad/obsolete credentials yield 401. The freshness read is the authorization linearization point: a request already validated before a change may complete afterward. For particularly sensitive administrative changes, lock and revalidate actor state inside the same transaction before the write. Do not promise cancellation of already executing requests; no cache is introduced. For multi-node deployment all nodes use the same DB and catalog version. Monitoring and load tests determine whether later changes are warranted.

Redis is not part of the MVP. A later cache behind the same port is an optimization only after measurement and a new approved consistency decision: PostgreSQL remains authoritative. A TTL or asynchronous invalidation can serve revoked state after commit and therefore weakens immediate post-commit revocation; a synchronous invalidation alone is not atomic with a PostgreSQL commit and races with stale fills, process crashes and partitions. Any future design must specify versioned entries, ordering/fencing, a durable change mechanism, restart and eviction recovery, maximum staleness, cache-hit validation guarantees, and failure/partition behavior; if strong freshness cannot be established, bypass cache to the primary DB or fail closed. Redis persistence, replication and failover do not turn cached values into durable authoritative security state. Include latency, network hops, memory, operations, availability and testing costs in the trade-off. No cached scheme may claim current guarantees until its invalidation and races are proven.

JSON login invokes an application use case, which calls `CredentialAuthenticationPort`; a security adapter invokes `AuthenticationManager` (typically `ProviderManager`) and `DaoAuthenticationProvider`, which uses `UserDetailsService` and `PasswordEncoder`. Translate the verified identity to application data; after authentication, lock/recheck active user and version before issuing a session. Issue JWT through `AccessTokenIssuerPort`; refresh generation and persistence are separate responsibilities. `CurrentActorPort` reads an immutable actor from security infrastructure. These ports represent actual external boundaries, not one interface per class. `JwtDecoder`, authentication conversion, `SecurityContextHolder`, framework `Authentication`, `GrantedAuthority` and servlet objects remain in adapters/configuration. Context is request execution state, normally thread-local in Servlet; framework lifecycle clears it and arbitrary asynchronous tasks do not automatically inherit it. Never put principal in mutable singleton fields. Standard filter/provider components validate Bearer credentials; the online freshness check is integrated into authentication with explicitly tested 401/503 failure mapping.

## Refresh family and transport

Use HTTPS and explicit JSON credentials, no auth cookies. Login returns `{accessToken, tokenType: "Bearer", expiresIn: 300, refreshToken}` with `Cache-Control: no-store`; refresh accepts `{refreshToken}` and returns a new pair; logout accepts `{refreshToken}`, revokes that family, returns 204 on a valid active or already revoked known family, and 401 for malformed/unknown credentials. Never log bodies or tokens. A client protects the opaque secret at rest, serializes refresh attempts, replaces the old token atomically and clears it on logout. No universal browser storage recommendation: a future browser client requires a separate XSS, cookie, CSRF, CORS and storage design.

Generate 32 cryptographically random bytes, encode unambiguously, persist SHA-256 digest only, with unique digest index. This is a high-entropy bearer secret, not a human password. Family has immutable user ID, absolute expiry 30 days and revoked state; token records have digest, family, issued/consumed times and expiry bounded by family expiration. Rotation uses PostgreSQL READ COMMITTED: locate digest, lock user then family in a consistent global lock order, re-read token/family/user under lock, reject inactive/expired state, mark token consumed and insert exactly one successor in one transaction. Revalidate user security state when issuing tokens. Family lock serializes refresh, logout and replay; optimistic locking alone needs careful retry semantics and is less direct here.

Atomic rotation and replay policy are distinct: the lock and transaction ensure at most one successor per token even if replay handling changes; the selected replay policy additionally revokes the whole family on a consumed-token presentation before family expiry. Commit that decision and security event, then return generic 401 outside the transaction. Do not throw a rollback-causing exception before commit. Concurrent legitimate refreshes are indistinguishable from theft: one can return a token pair, then the second revokes that entire family and invalidates that pair. This deliberate strict policy forces reauthentication; clients must single-flight refresh and never automatically replay a timed-out request. A grace window would improve usability but allow stolen-token replay; it is not selected. Redis atomic commands or distributed locks cannot identify whether a second presentation is legitimate, nor automatically make a PostgreSQL commit atomic with Redis; a lock is not a replay policy. Lost responses also require login again. Unknown or expired secrets yield generic 401 without enabling arbitrary family revocation. Retain consumed digests through family absolute expiry plus 7 days for replay/audit and delete expired families and records in a bounded operational cleanup; never persist plaintext. Logout and replay take effect for subsequent security-state reads, not requests already authorized.

## Administrator bootstrap and invariant

Provide an explicit one-shot operator command in the application distribution, never a public endpoint. It accepts an existing active registered user's ID and runs only under a deployment-controlled OS identity with privileged database access; no separate application bootstrap secret is required. Deployment access controls, database credentials and audit must establish operator authorization. It grants ADMIN only if no admin bootstrap has ever succeeded, and records completion atomically. No credential or default password in source, command-line history, or logs. Rerunning after success makes no privilege change; a different target is refused. A protected singleton database guard row initialized by migration is locked first for bootstrap and every role/status operation that may change the active-admin count; then lock affected users in stable ID order, evaluate count and update in the same transaction. Reject demotion/deactivation of the last active ADMIN, including self-actions; no delete-user operation in MVP. The first bootstrap is the only permitted transition from zero active admins. Database lock and transaction tests cover concurrent demotions and bootstrap. Recovery from lost admin access requires a separately documented privileged operational recovery process, not a public endpoint.

## API, verification and delivery

`/api/v1/auth/register`, `/login`, `/refresh`, `/logout`; `/api/v1/me`; `/api/v1/tasks`, `/tasks/mine`, `/tasks/{id}`, `/tasks/{id}/status`; `/api/v1/users`, `/users/{id}/roles`, `/users/{id}/status`. JSON DTOs map explicitly to application commands/results; JPA records never cross adapters. RFC 9457 errors do not expose internals. Rate-limit login and registration at a trusted ingress or a single-node application mechanism with explicit deployment assumptions; avoid permanent account lockout. Restrict Swagger outside development, no real credentials in examples. CSRF disabling is justified only while all credentials are explicit non-ambient headers/bodies; explicit CORS origin allowlists are not authorization.

Acceptance tests must exercise real signed JWT decoder, wrong issuer/audience/purpose/algorithm, malformed claims and expiry; 401/403/404 matrix; own/all pagination and non-owner mutation; role escalation; immediate post-commit user and family revocation and 503 DB failure; concurrent requests without principal leakage; PostgreSQL races for replay, logout, role updates and last-admin invariant; rollback-safe revocation; token cleanup; optimistic task conflicts; migrations and unique canonical keys. Architecture tests prohibit framework imports in domain/application and dependency cycles. Test login rate limiting, secret redaction, key rotation and documented in-flight request limits. Tests are specifications, not executed evidence.
